The search for "SQLite WAL replace database file while open in another process corruption backup API" returned the following summary:
Replacing or overwriting an SQLite database file on disk while it is actively open and in use by another process—especially when **WAL (Write-Ahead Logging) mode** is enabled—is a direct recipe for **database corruption or sudden application crashes**[1][2]. 

---

### Why File-Level Replacement Fails in WAL Mode

1. **Multiple Files Constitute the Database:** In WAL mode, SQLite relies on three files working in unison: `database.db` (the main file), `database.db-wal` (the write-ahead log containing recent committed transactions), and `database.db-shm` (shared memory index)[3][4]. 
2. **Stale/Mismatched WAL State:** If you overwrite only the main `database.db` file with a new version while leaving the old process running, the target process still holds an open file descriptor/handle to the *old* content, or it will look at the existing `-wal` and `-shm` files which do not match the new database pages[2][5]. This mismatch causes immediate logical corruption (`SQLITE_CORRUPT`)[6].
3. **OS-Level Locking Behavioral Differences:** 
   * On **Windows**, you cannot overwrite an open file at all; the file replacement operation will throw a "file in use / permission denied" error.
   * On **Linux/Unix**, you *can* delete or overwrite a file inode while a process has it open, but the running process keeps writing/reading the *old* unlinked file descriptor, meaning it will completely ignore your replacement file until restarted[2].

---

### The Correct Solutions

Depending on your workflow, you should use either the **SQLite Online Backup API** or coordinate a **clean application-level restart**.

#### Solution 1: Use the SQLite Online Backup API (Programmatic Replacement)
If you want to update/replace the contents of a live database cleanly without shutting down concurrent processes, **never overwrite files via shell commands (`cp`, `mv`, `rsync`)**. Instead, use SQLite’s built-in **Online Backup API** (`sqlite3_backup_init`, `sqlite3_backup_step`, `sqlite3_backup_finish`)[3][7].

The backup API acts *safely* across processes because it reads pages transactionally through SQLite's locking mechanism, safely handling WAL checkpoints on the fly.

* **In Python (`sqlite3`):**
  ```python
  import sqlite3

  # Open connection to the target (live) database that needs to be updated
  dst_conn = sqlite3.connect("/path/to/live_database.db")

  # Open connection to your new/source database file
  src_conn = sqlite3.connect("/path/to/new_replacement_data.db")

  with dst_conn:
    # Safely copy the source database over the live destination database page-by-page
    src_conn.backup(dst_conn)

  src_conn.close()
  dst_conn.close()
```
* **Via Command Line Shell (`sqlite3` CLI):**
  ```bash
  sqlite3 live_database.db ".restore new_replacement_data.db"
  ```
  *(Note: The `.restore` command uses the Backup API under the hood, safely pushing the new state into the target database even if other readers/writers are interacting with it).*

---

#### Solution 2: Graceful Close, Replace, and Reopen (For Full File Swaps)
If your goal is to completely swap out the physical database file from an external deployment script or installer, you **must coordinate with the processes holding it open**[2]:

1. **Signal the application(s)** running against the database to close their connections gracefully[2]. This forces SQLite to flush and checkpoint the `-wal` file into the main `.db` file and delete the `-wal`/`-shm` companion files[8][2].
2. **Perform the file replacement:** Safely swap/overwrite the `.db`, `.db-wal`, and `.db-shm` files simultaneously (or just the `.db` file if you are certain no WAL file exists post-checkpoint)[1][2].
3. **Restart the application(s)** so they open fresh file handles to the new database[2].
